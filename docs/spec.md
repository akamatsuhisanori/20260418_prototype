# Re:roots 仕様書

**バージョン**: 0.1
**最終更新**: 2026-04-18
**対象アプリ**: [Re:roots](https://20260418-prototype.vercel.app) — Nuxt 3 + Supabase + Vercel

---

## 0. このドキュメントの使い方

### 0-1 目的

このドキュメントは、Re:roots アプリの**振る舞い・UI コピー・データ構造**を記述した仕様書です。コードの実装を抽象化し、**自然言語の指示**で仕様変更できる形に整えてあります。

### 0-2 章番号の規約

章は大きく 2 つのパートに分かれます。

- **章 1〜6**：アセスメントのプロセス（ユーザーが操作する 6 画面）
- **章 7〜**：システム仕様（認証・管理画面・データモデルなど）

各章のサブセクションは `章-節` で表現します。例：`3-2` は「章 3 の節 2」。

**章 1〜6 のサブセクションは順序固定**です。どの章でも次の順序で並びます：

| 節 | 内容 |
|----|------|
| `X-1` | 目的・概要 |
| `X-2` | 回答形式（入力タイプ） |
| `X-3` | 画面コピー（見出し・説明・プレースホルダ・ボタン・バリデーション） |
| `X-4` | 遷移条件・バリデーション |
| `X-5` | データ保存（responses テーブルへの書き込み） |

これにより「`3-2` の回答形式」「`4-3` の画面コピー」といった指示が一意に解釈できます。

### 0-3 自然言語で編集するときの指示例

以下のパターンで指示してもらえると、差分が機械的に決まります。

| 指示 | 意味 |
|------|------|
| `X-Y の「AAA」を「BBB」に変更して` | 該当節の文言を置換（完全一致） |
| `X-Y の回答形式を 短文形式 から 選択形式 に変更して` | 回答形式フィールドの差し替え（選択肢候補は節 0-4 参照） |
| `X-Y に「CCC」を追加して` | 箇条書きや表に項目を追加 |
| `X-Y から「DDD」を削除して` | 箇条書きや表から項目を削除 |
| `章 1〜6 に 7 を追加して、XXX のようなページを追加して` | 新しいプロセス章を末尾に追加。以降の章番号（旧 7 以降）は +1 ずれる |
| `章 X と Y の順序を入れ替えて` | 章を入れ替え（プロセス章の場合は番号も再採番） |

### 0-4 回答形式の選択肢

`X-2 回答形式` で使える標準タイプは以下の 6 種類です。

| タイプ | 説明 | 現状の使用例 |
|--------|------|--------------|
| `短文入力` | 1 行のテキストボックス | 章 2（組織名入力） |
| `長文入力` | 複数行のテキストエリア | 章 5（エピソード記述）、章 6（対話・行動アイデア） |
| `スライダー（0-10）` | 0〜10 の数値スライダー | 章 3（人格形成度） |
| `選択形式（単一）` | ラジオボタン | 章 3（関わり頻度）、章 6 冒頭（要素選択） |
| `選択形式（複数）` | チェックボックス | 未使用 |
| `閲覧のみ` | 入力なし、表示とナビゲーションのみ | 章 1、章 4 |

### 0-5 用語集

| 用語 | 定義 |
|------|------|
| **回答者** | アセスメントを受ける一般ユーザー（`profiles.role = 'respondent'`） |
| **管理者** | 招待・エクスポートを行う運営者（`profiles.role = 'admin'`） |
| **アセスメント** | 章 1〜6 で構成される一連の自己診断プロセス |
| **ステップ** | 章 1〜6 の各プロセス。コード上の `state.meta.step` は `0〜5` で本書章番号 −1 |
| **サブステップ** | 章 6 内部の 5 段階（選択／対話／行動／プラン／完了） |
| **提出** | `responses.is_submitted = true` にする操作。以降回答は編集不可 |
| **組織** | 過去・現在にユーザーが所属したチーム・コミュニティ。最大 3 × 2 = 6 件 |
| **次元** | 自分らしさの 3 要素：情動的（Affective）／関係的（Relational）／エージェンシー（Agentic） |
| **RBS** | Reflected Best Self（映し出された最良の自己）の略。章 5 の理論的背景 |
| **招待制** | `invitations` テーブルに登録されたメールアドレスのみログイン可能 |

## 1. ステップ 1：イントロダクション

### 1-1 目的

アプリの全体像（Step 1〜5 で何をするか）をユーザーに提示し、アセスメント開始への同意を得る。初回訪問時は「はじめる」、途中保存データがある場合は「続きから」再開できる。

### 1-2 回答形式

`閲覧のみ`

### 1-3 画面コピー

**アプリ名**：「Re:roots」

**タグライン**：
- 「過去の組織経験から「自分らしさ」を解体し、」
- 「3人の自分との対話で行動の選択肢を見つける」

**見出し**：「このアプリでできること」

**プロセス概要（5 項目）**：

| アイコン | ステップ表記 | 説明 |
|----------|--------------|------|
| 🏢 | Step 1 | 過去・現在の所属組織を棚卸し |
| 📊 | Step 2 | 各組織とのアイデンティティの強さを測定 |
| 🗺️ | Step 3 | アイデンティティマップで隔たりを可視化 |
| 🔍 | Step 4 | 「自分らしさ」をポータブルな要素に解体する |
| 💬 | Step 5 | 3人の自分との対話で行動の選択肢を発見 |

**ボタン**：
- 初回：「はじめる →」
- 続きから：「続きから →」

### 1-4 遷移条件

- 「はじめる」／「続きから」ボタンのクリックで章 2（Step 1）へ遷移。
- 「続きから」表示の条件：過去か現在のいずれかに組織が 1 件以上入力済み、かつ未提出。

### 1-5 データ保存

- 章 1 では新しいデータを書き込まない。
- ページ表示時に `responses` の 1 行を `user_id` 紐付きで取得（無ければ空の `AssessmentState` を持つ行を作成）。

## 2. ステップ 2：組織の棚卸し

### 2-1 目的

過去と現在に所属した組織・チーム・コミュニティを列挙してもらう。以降のステップで分析する「対象組織リスト」を確定させる。

### 2-2 回答形式

`短文入力` × 6 スロット（過去 3・現在 3）

### 2-3 画面コピー

**見出し**：「Step 1：組織の棚卸し」

**説明文**：「これまで所属した組織・チーム・コミュニティを思いつく限り書き出してください。」

**ヒント**：「（例：高校の部活、大学のゼミ、研究室、1社目の会社、サークルなど）」

**プレースホルダ**：「組織名を入力...」

**ラベル・バッジ**：
- 現在セクション見出し：「現在所属中」
- 過去バッジ：「過去」
- 現在バッジ：「現在」
- 測定済バッジ：「✓ 測定済」
- 追加ボタン：「追加」
- 空状態：「組織をまだ追加していません」

**バリデーション文言**：「※ 過去の組織と現在の組織がそれぞれ最低1つ必要です」

**ボタン**：
- 戻る：「← 戻る」
- 次へ：「次へ：アイデンティティ測定 →」

### 2-4 遷移条件

- **次へ可能**：過去スロットに 1 件以上、現在スロットに 1 件以上、トリム後非空の組織名が入力されていること。
- **次へ不可**：いずれかの条件を満たさない場合、次へボタンは非活性、`2-3` のバリデーション文言を表示。

### 2-5 データ保存

- 書き込み先：`responses.data.orgs.past[0..2]`、`responses.data.orgs.current[0..2]`（いずれも `string[]`）
- 保存タイミング：入力変更から 600ms デバウンス後に `responses.data` 全体を `update`

## 3. ステップ 3：アイデンティティ測定

### 3-1 目的

章 2 で列挙した各組織について、「人格形成度」「関係的結びつき」「主体性」の 3 次元を 0〜10 で、関わり頻度を 5 段階で測定する。後続のバブルマップと解体ステップの原データ。

### 3-2 回答形式

- 3 次元スコア：`スライダー（0-10）` × 3 次元 × 組織数
- 関わり頻度：`選択形式（単一）` × 5 段階 × 組織数

**頻度の選択肢（値：ラベル）**：

| 値 | ラベル |
|----|--------|
| 5 | ほぼ毎日 |
| 4 | 週1回程度 |
| 3 | 月1回程度 |
| 2 | 年数回 |
| 1 | ほとんどない |

**スケール両端ラベル**：
- 低：「全く感じない」
- 高：「強く感じる」

**3 次元の定義**：

| 次元 ID | ラベル | アイコン | RBS 名 | 説明 | 質問文 |
|---------|--------|----------|--------|------|--------|
| `affective` | 没頭と意味 | 🔥 | 情動的資源（Affective Resources） | ポジティブな感情・自己肯定感・仕事への充実感 | 時間を忘れるほど没頭でき、心から意味を感じていた活動や瞬間はどんなものでしたか？ |
| `relational` | つながりと居場所 | 🤝 | 関係的資源（Relational Resources） | 信頼関係・承認・所属感・つながりの質 | 周囲から認められ、「ここが自分の場所だ」と感じていた理由は何でしたか？ |
| `agentic` | 主体性と手応え | ⚡ | エージェンシー資源（Agentic Resources） | 自律性・自己効力感・行動が成果に結びつく感覚 | 自分の意志で主体的に動き、行動が成果に結びついて手応えを感じていた場面はどんな時でしたか？ |

（※ 章 3 では「人格形成度」単体としてまとめて表示、章 5 で 3 次元それぞれを個別に問う）

### 3-3 画面コピー

**見出し**：「Step 2：アイデンティティ測定」

**説明文**：「各組織について、あなたとの心理的なつながりを測定します。」

**次元ラベル**：
- 人格形成度：「人格形成度」
- 人格形成度の説明：「今の自分の性格・価値観・考え方を、この組織での経験がどのくらい形作っていると思いますか？」
- 関わり頻度：「現在の関わり頻度」
- 関わり頻度の説明：「現在、この組織のメンバーとどのくらい関わっていますか？」

**ナビゲーション（組織間）**：
- 前の組織：「← 前の組織」
- 次の組織：「次の組織 →」

**ナビゲーション（ステップ間）**：
- 戻る：「← 戻る」
- 次へ：「次へ：隔たりを可視化 →」

### 3-4 遷移条件

- **組織間ナビ**：最初の組織以外で「前の組織」、最後の組織以外で「次の組織」を表示。
- **次へ可能**：全組織で 3 次元すべてが 0 より大きい値かつ頻度が選択済み。
- **次へ不可**：未入力組織が残っている場合は次へボタン非活性。

### 3-5 データ保存

- `responses.data.dimensions.{past|current}[orgName][dimId]`（0-10 の数値）
- `responses.data.frequencies.{past|current}[orgName]`（1-5 の数値）
- 保存タイミング：スライダー／ラジオ変更から 600ms デバウンス。

## 4. ステップ 4：隔たりの可視化

### 4-1 目的

章 3 で測定したスコアをバブルマップとして表示し、過去と現在のアイデンティティの隔たりを視覚的に提示する。数値サマリーと所感メッセージを添えて、次の「解体」ステップへ動機づける。

### 4-2 回答形式

`閲覧のみ`

### 4-3 画面コピー

**見出し**：「Step 3：隔たりの可視化」

**説明文**：「バブルの大きさ = アイデンティティの強さ、中心からの距離 = 現在の関わりの少なさ」

**バブルマップ凡例**：
- 過去の組織バブル：「過去の組織」
- 現在の組織バブル：「現在の組織」
- 凡例キャプション：「円の大きさ = アイデンティティの強さ」
- 中央ラベル：「自分」

**関わりリング（中心からの距離帯）**：

| 距離比 | ラベル |
|--------|--------|
| 0.30 | 深い関わり |
| 0.55 | 中程度 |
| 0.80 | 薄い関わり |

**ツールチップ項目**：
- 「IDスコア」
- 「人格形成度」
- 「関わり頻度」

**隔たりスコア**：
- ラベル：「隔たりスコア」
- 「アイデンティティ形成度トップ：」
- 「現在：」

**所感メッセージ（隔たりスコア別）**：

| しきい値 | メッセージ |
|----------|------------|
| 隔たり ≥ 3 | あなたが最も「自分らしい」と感じた環境と今の環境には大きな距離があります。次のステップで「自分らしさ」を具体的に解体し、今の環境や別の場でも発揮できる形に変換しましょう。 |
| 隔たり ≥ 1 | 過去の経験と今の環境には一定の距離があるようです。次のステップで「自分らしさ」の具体的な要素を紐解いてみましょう。 |
| それ以外 | あなたの過去の経験と今の環境は比較的つながっています。次のステップでさらに深掘りし、自分らしさをより鮮明にしましょう。 |

**サマリーテーブル列**：「組織」「種別」「IDスコア」「人格形成度」「関わり頻度」

**遷移文（動的に組み立て）**：
- 導入：「次のステップでは」
- Part 1：（トップ過去組織名）「での経験の中にある「自分らしさ」を具体的に紐解いていきます。」
- Part 2A：「「自分は【」（トップ過去組織名）「】の人間だ」という捉え方から、」
- Part 3：「「自分はこういう要素を大事にする人間だ」という捉え方に変えることで、」
- Part 4：「自分らしさを今の環境でも、別の場でも発揮できるようになります。」

**ボタン**：
- 戻る：「← 戻る」
- 次へ：「次へ：自分らしさを紐解く →」

### 4-4 遷移条件

- 章 3 のデータが全て埋まっていれば常に「次へ」可能。
- 章 2 の時点で 1 組織でも未入力の場合は章 4 に到達しない（章 3 で止まる）。

### 4-5 データ保存

- 章 4 では新規書き込みなし（閲覧のみ）。
- 「隔たりスコア」「トップ組織」などはフロントで都度計算（DB には保持しない）。

## 5. ステップ 5：自分らしさの解体

### 5-1 目的

章 4 で見えた「トップ過去組織」での経験を、3 次元（情動／関係／エージェンシー）に分解し、特定の組織に依存しない **ポータブルな一言キーワード** として言語化する。

### 5-2 回答形式

- エピソード：`長文入力` × 3 次元
- キーワード：`短文入力` × 3 次元

### 5-3 画面コピー

**見出し**：「Step 4：自分らしさを紐解く」

**イントロ（動的）**：
- Part A：「「自分は【」
- Part B：（トップ過去組織名）「】の人間だ」」
- Part C：「という大きなかたまりを、特定の組織に依存しないポータブルな要素に分解していきます。」
- 組織名フォールバック：「その組織」

**3 次元それぞれのカード構成**：
- アイコン＋ラベル＋ RBS 名（節 3-2 の表を参照）
- 質問文：「【」（組織名）「】にいた頃、」＋（節 3-2 の質問文）
- ヒント（次元別）：

| 次元 | ヒント |
|------|--------|
| affective | どんな仕事・プロジェクト・場面か。「これには意味がある」と感じた理由も含めて |
| relational | どんな人間関係・文化・環境の中にいたか。どう見られていたか |
| agentic | 任されていた役割・裁量の範囲・どんな成果・貢献があったか |

- エピソードプレースホルダ：「具体的な場面・エピソードを自由に書いてください...」
- キーワード誘導：「→ これを一言で言うと？（組織名を使わずに）」
- キーワードプレースホルダ：「一言キーワード」
- キーワード例（次元別）：

| 次元 | 例 |
|------|----|
| affective | 例：「目的志向のチームでの議論と成果物づくり」 |
| relational | 例：「対等に意見を出し合える文化と深い信頼関係」 |
| agentic | 例：「裁量を持ってプロジェクトを動かし、チームの成果に直接貢献する」 |

**完成カード（全キーワード入力後に表示）**：
- タイトル：「✨ あなたの「自分らしさ」カード」
- サブ：「「自分は【」（組織名）「】の人間だ」ではなく——」
- フッター 1：「——こういう要素を大事にする人間です。」
- フッター 2：「これらは特定の組織に紐づくものではなく、今の環境でも別の場でも発揮できます。」

**ボタン**：
- 戻る：「← 戻る」
- 次へ：「次へ：3人の自分と対話する →」

### 5-4 遷移条件

- **次へ可能**：3 次元すべてのキーワードがトリム後 1 文字以上（エピソードは任意）。
- **次へ不可**：キーワード未入力が 1 つでもある場合。

### 5-5 データ保存

- `responses.data.dialogue["step4:{dimId}:episode"]`（長文）
- `responses.data.dialogue["step4:{dimId}:keyword"]`（短文）
- `dimId` は `affective` / `relational` / `agentic`。

## 6. ステップ 6：3人の自分との対話と行動計画

章 6 は内部で 5 つのサブステップに分かれる（`state.meta.subStep = 0..4`）。

- `6-A 要素選択`（subStep 0）
- `6-B 3人の対話`（subStep 1）
- `6-C 行動アイデア`（subStep 2）
- `6-D 今週のプラン`（subStep 3）
- `6-E 完了表示`（subStep 4）

### 6-1 目的

章 5 のキーワードから 1 つを選び、その要素について「過去の自分」「今の自分」「未来の自分」が同じ問いに答える対話形式で深掘りし、最終的に **今週 1 つだけ試す行動** を決める。

### 6-2 回答形式

| サブステップ | 入力タイプ |
|--------------|-----------|
| 6-A 要素選択 | `選択形式（単一）` × 3 次元 |
| 6-B 対話 | `長文入力` × 3 質問 × 3 時点（9 セル） |
| 6-C 行動アイデア | `長文入力` × 3 方向性 |
| 6-D 今週のプラン | `長文入力` × 1 |
| 6-E 完了表示 | `閲覧のみ` |

### 6-3 画面コピー

#### 6-3-A 要素選択（subStep 0）

- リード：「「自分らしさ」カードの中から、」
- 強調：「今最も取り戻したい・深めたい要素を1つ」
- 末尾：「選んでください。」
- ヒント：「（エピソードが長かったものが自動選択されています。変更可能です）」
- 選択済みチップ：「✓ 1つ選択中」
- 未選択チップ：「1つ選んでください」
- 次へ：「次へ：対話を始める →」

#### 6-3-B 対話（subStep 1）

- 見出し：「Step 5：3人の自分の対話」
- 説明：「選んだ要素について、3人の自分が同じ問いに答えます。思いつくままに書いてください。」

## 7. アセスメント全体フロー

### 7-1 ナビゲーションルール

- 各章のナビゲーションは「戻る／次へ」のみ。任意章への直接ジャンプは不可。
- 戻ると入力内容は保持される（上書きも可能）。
- 章 4（可視化）と章 6-E（完了）は閲覧のみのためバリデーションによる非活性は発生しない。

### 7-2 プログレス表示

- 章 2〜6 を「5 段階」として上部に ProgressBar を表示（章 1 は非表示）。
- 各セグメントのラベル（左→右）：「棚卸し」「測定」「可視化」「解体」「行動」
- 現在の章は強調表示、完了した章は塗りつぶし。

### 7-3 自動保存・提出状態

- 入力変更は 600ms デバウンスで `responses.data` を部分 `update`。
- ヘッダー表示：
  - 未提出時：「自動保存中」
  - 提出済時：「送信済み（閲覧のみ）」
- 提出済レスポンスは全ステップ閲覧可能だが、全入力が非活性。

### 7-4 章追加時のルール（将来拡張）

- 新しいプロセス章を追加する場合、章番号を末尾に追加し、ProgressBar ラベル配列にも対応する項目を追加する。
- 既存章の番号は原則ずらさない。途中挿入が必要な場合は本書と実装コードの両方で連動して再採番する。

## 8. 認証（Magic Link + 招待制）

### 8-1 ログイン方式

- Supabase Auth の **Magic Link**（パスワードレス）。
- 宛先メールアドレスは `invitations` テーブルに登録済みである必要がある（招待制）。
- 例外：`NUXT_ADMIN_EMAIL` に設定されたメールは常にログイン可能（ブートストラップ管理者）。

### 8-2 ログインフロー

1. ユーザーが `/login` でメールアドレスを入力し送信。
2. フロントが `POST /api/invite/check` で招待済判定。
3. OK なら `supabase.auth.signInWithOtp` で Magic Link を送信。
4. ユーザーがメール内のリンクをクリック → `/confirm` に戻ってくる。
5. `/confirm` は Supabase が自動でセッション cookie を設定。`useSupabaseUser()` が値を持ったら `/` にリダイレクト。
6. 新規ユーザーの場合、`handle_new_user` トリガーが `profiles` を自動作成し、該当 `invitations` 行を `status = 'accepted'` に更新。

### 8-3 ログイン画面コピー

- 見出し：「ログイン」
- 説明：「登録したメールアドレスを入力してください。確認用のリンクをお送りします。」
- プレースホルダ：「name@example.com」
- 送信ボタン：「リンクを送る」
- 送信後見出し：「メールを確認してください」
- 送信後本文：「届いたリンクをクリックするとログインが完了します。」
- 送信エラー：「送信に失敗しました。もう一度お試しください（未招待のメールアドレスは送信できません）」
- 未招待エラー：「このメールアドレスは招待されていません。管理者に連絡してください。」

### 8-4 ルートガード

全ルートにグローバルミドルウェアを適用。

| パス | 要件 |
|------|------|
| `/login`, `/confirm` | 認証不要（公開） |
| 上記以外 | ログイン必須。未ログインなら `/login` にリダイレクト |
| `/admin/*` | ログイン＋`profiles.role = 'admin'`。非管理者は `/` にリダイレクト |

## 9. 招待管理

### 9-1 目的

管理者が回答者のメールアドレスを `invitations` テーブルに登録し、Magic Link を送信する。

### 9-2 画面（/admin/invitations）

**上部**：新規招待追加フォーム
- メール入力（必須）
- メモ入力（任意、プレースホルダ「メモ (任意)」）
- 「招待を追加」ボタン

**下部**：招待リスト（招待日降順）
- カラム：メール、状態、メモ、招待日、アクション
- 状態ラベルと色分け：

| コード値 | 表示ラベル | バッジ |
|----------|------------|--------|
| `pending` | 招待済 | 標準 |
| `sent` | 送信済 | 標準 |
| `accepted` | ログイン済 | 緑 |
| `submitted` | 提出済 | 緑 |
| `revoked` | 失効 | 赤 |

- アクション（失効以外のとき）：
  - 「リンク送信」または「再送」
  - 「失効」（確認ダイアログ：「この招待を失効させますか？」）

### 9-3 API

| エンドポイント | 権限 | 挙動 |
|----------------|------|------|
| `POST /api/invite/check` | 誰でも | `{ email }` を受け取り、招待済か判定。ADMIN_EMAIL は常に OK |
| `POST /api/invite/create` | 管理者 | 新規招待を追加（既存ならステータス `pending` に戻す） |
| `POST /api/invite/send` | 管理者 | Supabase Auth Admin API で招待メール送信、既存ユーザーなら OTP にフォールバック |

### 9-4 招待の失効フロー

- `invitations.status = 'revoked'` に更新。
- 以降 `/api/invite/check` は `{ ok: false, reason: 'not_invited' }` を返す。
- すでにログイン済のユーザーのセッションは即座には切れない（Supabase 側セッション有効期限まで）。必要なら管理者が Supabase Auth UI でユーザーを削除する。

### 12-1 テーブル一覧

| テーブル | 用途 |
|----------|------|
| `profiles` | `auth.users` と 1:1 の拡張プロフィール（role 管理） |

### 12-2 profiles

| カラム | 型 | 制約・既定 | 備考 |
|--------|----|----------|----|
| `id` | uuid | PK, FK to auth.users(id), on delete cascade | |
| `email` | text | unique | |
| `role` | text | not null, default 'respondent', check in ('admin','respondent') | |
| `display_name` | text | nullable | |
| `created_at` | timestamptz | default now() | |
| `updated_at` | timestamptz | default now()、トリガーで自動更新 | |

### 12-3 invitations

| カラム | 型 | 制約・既定 | 備考 |
|--------|----|----------|----|
| `id` | uuid | PK, default gen_random_uuid() | |
| `email` | text | unique | |
| `status` | text | not null, default 'pending', check in ('pending','accepted','revoked') | |
| `note` | text | nullable | 管理者メモ |
| `invited_by` | uuid | FK to profiles(id), on delete set null | |
| `invited_at` | timestamptz | default now() | |
| `accepted_at` | timestamptz | nullable | ログイン完了時刻 |

**インデックス**：`invitations_status_idx (status)`

### 12-4 responses

| カラム | 型 | 制約・既定 | 備考 |
|--------|----|----------|----|
| `id` | uuid | PK, default gen_random_uuid() | |
| `user_id` | uuid | unique, not null, FK to profiles(id), on delete cascade | |
| `data` | jsonb | default '{}' | `AssessmentState` を丸ごと格納 |
| `is_submitted` | boolean | default false | |
| `started_at` | timestamptz | default now() | |
| `updated_at` | timestamptz | default now()、トリガーで自動更新 | |
| `submitted_at` | timestamptz | nullable | |

**インデックス**：`responses_submitted_idx (is_submitted)`

### 12-5 responses.data の構造（AssessmentState）

```
{
  orgs: { past: string[3], current: string[3] },
  frequencies: { past: { [orgName]: 1-5 }, current: { [orgName]: 1-5 } },
  dimensions: {
    past: { [orgName]: { affective: 0-10, relational: 0-10, agentic: 0-10 } },
    current: { [orgName]: { ... } }
  },
  dialogue: { [key: string]: string },    // 章 5／章 6 の自由記述を dynamic key で格納
  actions: {
    craftExperiments: string,
    shiftConnections: string,
    makeSense: string
  },
  meta: {
    step: 0-5,                            // コード上の step 値（本書章番号 -1）
    subStep: 0-4,                         // 章 6 のサブステップ
    updatedAt: ISO8601
  }
}
```

### 12-6 トリガー・関数

- `set_updated_at()`：profiles／responses の `updated_at` を更新前に now() に設定。
- `handle_new_user()`：`auth.users` への insert 時に発火。
  - `profiles` を作成（メールが `NUXT_ADMIN_EMAIL` と一致すれば role=`admin`、それ以外は `respondent`）。
  - 該当 `invitations` 行を `status='accepted'`, `accepted_at=now()` に更新。
- `is_admin(uid uuid)`：SECURITY DEFINER。`profiles.role='admin'` を返す。RLS ポリシー内で使用。

## 13. 権限・RLS ポリシー

### 13-1 profiles

- SELECT：自分自身または管理者のみ。
- UPDATE（自分）：`display_name` のみ変更可能。`role` は変更不可。
- UPDATE（管理者）：任意の行・列を変更可能。
- INSERT：直接は禁止。`handle_new_user` トリガー経由のみ。

### 13-2 invitations

- 管理者のみ ALL（select/insert/update/delete）。
- 回答者からは一切読めない（`/api/invite/check` は service_role で判定）。

### 13-3 responses

- SELECT：自分自身または管理者。
- INSERT：`user_id = auth.uid()` のみ。
- UPDATE（自分）：自分の行のみ。
- UPDATE（管理者）：任意の行（インポート用途）。
- DELETE：管理者のみ。
